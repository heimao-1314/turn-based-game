## 1. 结论摘要

宠物系统应从当前“宠物 ID + 等级线性属性”升级为“宠物模板 + 宠物实例 + 服务端成长快照”。

本设计确定以下主线：

1. 每只宠物必须有独立实例，绑定、等级、进化、转生、资质、潜力、属性点、技能和装备都归属于实例。
2. 宠物达到 100 级后才可转生。
3. 宠物只有完成绑定后才可进化；绑定是不可逆操作，绑定后不可交易。
4. 进化采用独立修炼经验：先使用宠物修炼册获得修炼经验，经验满后消耗神品或魂品宠物进化书完成一次进化。
5. 神品进化获得 3 点随机天赋点和 1 点可分配天赋点；魂品进化获得 2 点随机天赋点和 2 点可分配天赋点。
6. 生命、攻击、防御、速度、法力按资质和属性点计算，装备与百分比来源进入统一结算管线。
7. 人物、佣兵、宠物统一使用相同的五项最终属性上限。
8. 最终属性在全部合法来源计算完成后再执行上限截断，同时保留截断前原始值供预览和排错。
9. 客户端只提交操作意图，等级、属性点、绑定、进化、转生、技能槽、装备和最终战斗属性全部以服务端为准。
10. 两张资料表均作为规则参考，不把其中有错误或缺少边界的 Excel 公式原样移植到生产代码。
11. 宠物1级出生属性使用统一的 `petQualificationScale = 4`；人物初始属性只作整体数量级参照，不直接叠加到宠物，佣兵不作为宠物数值标尺。

宠物元素属性不由宠物装备提供，而由元素转换任务写入宠物实例。五行相克顺序、无属性目标的 20% 伤害加成和新区五项属性上限在来源原文中引用人物系统开发文档；该资料未随本次资料纳入项目，宠物战斗只读取服务端生成的元素快照。

## 4. 已确认的核心规则

### 4.1 人物、佣兵、宠物统一属性上限

| 属性 | 字段 | 最终上限 |
| --- | --- | ---: |
| 生命 | `hp` | 5,000,000 |
| 攻击 | `attack` | 500,000 |
| 防御 | `defense` | 500,000 |
| 速度 | `speed` | 100,000 |
| 法力 | `mana` | 100,000 |

上限规则：

```text
effectiveStat = min(rawStat, hardCap)
```

- `rawStat` 是所有资质、属性点、潜力、贴纸、天赋、技能和装备效果结算后的原始值。
- `effectiveStat` 是战斗实际使用值。
- 服务端响应同时返回两者；客户端不得自行突破上限。
- 属性预览中若 `rawStat > hardCap`，显示“已达上限”和溢出值，不应让溢出值参与战斗。
- 人物、佣兵、宠物全部使用本表，不允许三个模块各自保存一套不同上限。

当前 `server/server-game-config.js` 已经使用全角色共享的 `STAT_LIMITS`，但其中仍是旧上限：生命 1,500,000、攻击/防御 250,000、速度 30,000、法力 50,000。后续实现应直接更新统一权威配置，并同步验证人物、佣兵、宠物三个属性入口，不再建立宠物专属上限。

### 4.2 转生条件

已确认规则：

- 宠物等级达到 100 级后，可以进行转生。
- 等级不足 100 时，服务端拒绝转生，不能只依赖客户端隐藏按钮。
- 转生必须针对玩家当前拥有的具体宠物实例。
- 宠物最多完成 2 次转生；达到 2 转后不能再次提交转生。
- 转生使用“宠物转生宝石”：放入 1 个时成功率为 75%，放入 2 个时成功率为 100%，不接受 0 个或 2 个以上的数量。
- 转生成功后，宠物普通等级回到 1 级，普通经验清零。
- 转生成功后，进化等级、进化随机天赋点、进化可分配天赋点和已经完成的天赋分配全部保留。
- 转生概率必须由服务端判定并记录请求 ID、宠物转生宝石数量、概率、随机结果和转生前后状态；重复请求不得重新随机或重复扣除材料。

使用 1 个宠物转生宝石且 75% 判定失败时，宠物转生宝石仍然消耗；失败时不得改变等级、经验、转生次数、进化等级或天赋点。

### 4.3 绑定与进化条件

已确认规则：

- 宠物绑定后不可交易。
- 宠物完成绑定后才可以进行进化。
- 未绑定宠物请求进化时，服务端返回 `pet_binding_required`。
- 绑定不可撤销，进化入口不得自动静默绑定宠物。

推荐交互：

```text
您即将绑定该宠物
[宠物头像] 宠物名字
绑定后不可交易，且无法解除绑定。

左下角：√绑定    右下角：X返回
```

绑定成功后使用标准结果对话框，不再次弹回宠物操作菜单。进化等级上限为 100 级，每本宠物修炼册增加 100 点修炼经验，各级需求按第 6.2.1 节正式方案执行。

### 4.4 战魂宠分类与觉醒

战魂宠是独立于野宠、神兽、魂兽、圣兽、S圣兽、SS圣兽、珍奇和绝世的独立宠物类别，分类标识使用 `battle_soul`。战魂宠通过英雄使者觉醒获得，不进入普通捕捉、召唤卷轴或绝世种子流程。

已确认觉醒材料：勇者之心 2,500 个、五系元素结晶各 50 个、英雄的战歌 50 个。勇者之心在每天 13:30～18:30 的英雄之路活动中由任意怪物掉落；普通元素之王的结晶掉率为 1%，真.元素之王为 10%；英雄的战歌来自神秘商店或玩家交易。原图结晶口径为风、火、土、水、木，与新区战斗元素金、木、水、火、土暂不强行映射。

觉醒提交必须在服务端事务内完成材料校验、扣除、宠物实例创建和首次奖励写入，并使用 `requestId` 保证幂等。首次获得战魂宠会关联英雄之路称号、高级成就“英雄传说”、迷失国度卡妙发放的 3 张天赋点卡，以及人物不良抗性成长卡兑换资格；这些奖励必须设置一次性领取标记，不能因重复觉醒或交易重复获得。

战魂宠可以交易；绑定后继续遵守统一的不可交易规则。当前已确认战魂宠名单为圣魔导师.荻拉、神箭手.露西娜、剑圣.巴诺什；三只均已有资质、普通技能归档组合和天生技能资料。剑圣.巴诺什的普通技能固定为强力A、致命A、暴伤A。

### 4.5 北极活动宠分类

北极活动宠是独立的活动限定分类，分类标识使用 `arctic_event`。当前仅建立名称占位，不代表已经确认召唤方式、活动周期、绑定/交易规则或正式品阶。北极活动宠不并入野宠、SS圣宠或其他召唤卷轴分类。

北极活动宠的获取活动、开放时间、是否可交易、是否可绑定、活动结束后的存量处理和重复获得规则，待活动方案确认后再写入正式配置。活动时间应使用统一服务器时间。

## 5. 领域模型

### 5.1 模板与实例必须分离

宠物模板描述“这是什么宠物”，宠物实例描述“玩家拥有的这一只宠物”。

宠物模板建议结构：

```json
{
  "templateId": 832,
  "name": "白色幻影",
  "category": "rare",
  "baseSprites": {
    "walkChjId": null,
    "attackChjId": null
  },
  "costumeSprites": [
    {
      "costumeId": "pet_costume_x",
      "name": "待补",
      "walkChjId": null,
      "attackChjId": null
    }
  ],
  "moveSpriteId": 832,
  "battleSpriteId": 833,
  "baseQualifications": {
    "hp": 2750,
    "attack": 3780,
    "speed": 5500,
    "mana": 3430,
    "defense": 1716
  },
  "innateSkillId": "pet_active_d4864f6c94",
  "ordinarySkillIds": ["pet_passive_x", "pet_passive_y", "pet_passive_z"]
}
```

`baseSprites` 记录宠物本体的行走/攻击 `chj`；`costumeSprites` 按时装逐套记录替换后的行走/攻击 `chj`。已确认编号填写整数，未找到资源时保留 `null`，禁止按名称猜测。野宠固定使用空数组 `costumeSprites: []`，不支持时装；只有明确具备时装穿戴功能的高级宠物才配置时装形象。野宠的 `ordinarySkillIds` 直接引用《宠物资料与资质合成汇总》20.2A 的固定组合。

`category`使用固定枚举：`wild`、`divine`、`soul`、`saint`、`s_saint`、`ss_saint`、`rare`、`peerless`、`battle_soul`、`arctic_event`。北极活动宠必须显式保存`arctic_event`，不能通过名称、活动地图或技能前缀临时推断分类；战魂宠同理必须显式保存`battle_soul`。

宠物实例建议结构：

```json
{
  "instanceId": "pet_01J...",
  "templateId": 832,
  "ownerAccount": "account_id",
  "equippedCostumeId": null,
  "bound": false,
  "level": 1,
  "exp": 0,
  "evolutionLevel": 0,
  "evolutionTrainingExp": 0,
  "evolutionAssignablePointsEarned": 0,
  "evolutionRandomPoints": {
    "hp": 0,
    "attack": 0,
    "speed": 0,
    "mana": 0
  },
  "rebirthLevel": 0,
  "allocatedPoints": {
    "hp": 0,
    "attack": 0,
    "speed": 0,
    "mana": 0,
    "defense": 0
  },
  "qualifications": {
    "base": {},
    "red": {},
    "card": {},
    "gem": {}
  },
  "potential": 0,
  "stickers": [],
  "talentEffects": [],
  "skillSlots": {},
  "equipment": {},
  "talentFormulaVersion": 1,
  "stateVersion": 1
}
```

时装穿戴状态属于宠物实例。渲染时若 `equippedCostumeId` 有效，行走和攻击分别读取对应时装的 `walkChjId`、`attackChjId`；未穿戴、时装失效或宠物不支持时装时回退到 `baseSprites`。时装形象只替换显示资源，不得隐式修改资质、技能或战斗属性；若某件时装另有属性效果，必须作为独立配置和属性来源记录。

旧实现曾以数值宠物 ID 同时表示模板和玩家拥有物，并限制同种宠物默认只能出现一次；这属于待删除的旧状态，不是新宠物系统规则。新系统使用不可复用的 `instanceId` 区分实例，并继续用 `templateId` 查找名称、图像和基础资质；同种宠物和同名宠物均允许重复拥有。

### 5.2 资质来源分栏

资质不能只保存一个最终数字。至少应分开保存：

| 来源 | 字段 | 用途 |
| --- | --- | --- |
| 宠物原始资质 | `base` | 模板或实例出生时的基础值 |
| 红色/加成资质 | `red` | 资质宝石镶嵌提升形成的红色/加成显示值 |
| 资质卡加成 | `card` | 独立规则来源 |
| 宝石卡/装备资质 | `gemCard` | 宝石卡、装备或镶嵌提供的资质 |

四类来源在实例中保持独立，以便预览、提取、交易和绑定规则解释来源；潜力换算防御时则读取防御单项的四类资质总和。

资质波动范围按宠物来源区分：

- 野宠：捕捉或生成时的出生资质允许浮动，浮动结果写入宠物实例；后续查看、交易和战斗读取已保存结果，不因刷新菜单重新随机。
- 非野宠：神兽、魂兽、圣兽、S圣兽、SS圣兽、珍奇、绝世、战魂宠、北极活动宠及其他固定来源宠物使用模板固定资质，不进行出生随机；实例只保存模板引用和后续培养、提资、宝石、装备等变化。
- 资质宝石镶嵌、红色/加成资质、合成或提资结果仍属于实例来源，不能反过来修改非野宠的固定出生资质定义。

## 6. 等级、进化、转生与属性点

### 6.1 等级边界

| 项目 | 规则状态 | 数值 |
| --- | --- | ---: |
| 普通等级下限 | 现有实现 | 1 |
| 普通等级上限 | 已确认/现有实现 | 100 |
| 达到转生条件 | 已确认 | 100 级 |
| 进化等级上限 | 已确认 | 100（独立于普通等级） |
| 最大转生次数 | 已确认 | 2 |

经验值必须是非负安全整数。普通等级经验使用三套独立曲线：未转生 1～100 级、1 转 1～100 级、2 转 1～100 级；三套曲线分别配置，不能从属性公式反推。最高状态为 2 转 100 级。转生成功后切换到下一套曲线并回到 1 级、普通经验清零；进化等级独立保存并继续保留。

### 6.1A 宠物 1 级出生属性

人物和佣兵现有实现都具备独立的 1 级 `baseStats`，说明等级成长不能在 1 级产生全 0 属性；但佣兵是按职业模板直接给出成熟基础属性，不能作为宠物出生属性的数值标尺。宠物1级只参考人物初始模板的整体数量级，不直接叠加人物的五项数值；人物用于平衡参照，佣兵只用于确认“1 级基础值 + 后续成长”的数据结构。

三类单位可以共用以下计算结构，但各自使用独立的基础值和成长规则：

```text
level1BaseStats = 模板在 1 级的非零出生快照
levelGrowthStats = 每次从 n 级升到 n+1 级增加的成长
levelStats = level1BaseStats + levelGrowthStats × (level - 1)
```

宠物采用“资质驱动的出生基数”，不为每只宠物手填一套与资质脱节的绝对属性：

```text
birthGrowthUnits = 1                         # 1 级自然成长单位，不计入天赋点总账
levelGrowthUnits = petLevel - 1              # 零转升级固定点
talentGrowthUnits = evolutionRandom + allocated

birthStat = baseQualification × 1.1 ÷ statCoefficient
            × petQualificationScale × birthGrowthUnits
pointGrowthStat = weightedQualification ÷ statCoefficient
                  × (levelGrowthUnits + talentGrowthUnits)
rawPetStat = birthStat + pointGrowthStat
```

人物初始模板（生命148、攻击20、防御0、速度5、法力30）只用于观察宠物整体数量级，不作为宠物五项属性的加法底座。`petQualificationScale` 当前正式确定为 `4`，只作用于1级隐藏自然成长单位，不放大后续零转固定点、进化随机点或玩家分配点。法力与速度仍由各自换算常量决定，不再额外加人物法力30。

以小白狼.天照为例，忽略红色资质、宝石、装备和百分比，使用 `petQualificationScale = 4` 时1级约为：生命135、攻击27、速度4、法力3、防御17。速度换算常量为2081.51，法力换算常量为1388.73；相同资质下法力约为速度的1.5倍，二者应保持同一数量级。该结果只表示出生平衡锚点，不代表最终战斗属性；最终仍要经过统一取整和属性上限。

出生规则：

- 1 级实例固定为 `level = 1`、普通经验 0、未分配属性点 0、进化随机点 0、装备和宝石加成为 0。
- 野宠只随机出生资质；非野宠读取固定模板资质。两者都不在创建实例时额外随机属性点。
- `birthGrowthUnits` 不显示为可分配点，也不计入现有满养成 `1243` 点校验；它只负责让 1 级拥有资质对应的基础属性。
- 从 1 级升到 2 级才增加第一份零转固定点，保留现有 `fixedPointsPerStat = petLevel - 1` 和满级总点规则。
- 属性先保留原始小数，统一按全局取整策略生成显示值和战斗快照；若资质大于 0 但取整结果为 0，1 级显示至少为 1，避免出现可操作但完全没有该属性的宠物。
- 出生强度以人物1级整体数量级为第一锚点，再用宠物自己的1级怪物承伤、击杀回合、技能公式、零转100级目标值和满养成上限校准；不得把人物五项属性直接加到宠物，也不得用佣兵1级面板反推宠物系数。

1级属性点明细：

| 项目 | 攻击 | 生命 | 速度 | 法力 | 防御 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 零转固定属性点 | 0 | 0 | 0 | 0 | 0 |
| 玩家可分配属性点 | 0 | 0 | 0 | 0 | 0 |
| 进化随机天赋点 | 0 | 0 | 0 | 0 | 0 |
| 1级自然成长单位（隐藏） | 1 | 1 | 1 | 1 | 1 |

因此，“属性点”菜单在1级应显示五项均为0点；“实际属性”菜单则按资质公式显示换算结果。以小白狼.天照和 `petQualificationScale = 4` 为例，实际值约为攻击27、生命135、速度4、法力3、防御17。不同宠物的实际值会随资质变化，但1级的点数结构相同。

不建议继续沿用旧运行时宠物的 `15000/2500/500` 等线性出生值：那套值对应旧属性上限，直接保留会与新区资质、人物和佣兵的统一计算管线冲突。

### 6.1B 野宠出生资质档次与颜色

野宠的出生资质只在捕捉/生成时随机一次，随机范围由该宠物的带出等级和五项资质上下限共同决定。正式采用四档资质，不增加第五档：

| 档次 | 颜色语义 | 颜色 token | 单项出生值区间 | 权重 |
| --- | --- | --- | --- | ---: |
| 差 | 普通白色 | `white` | 最低值 ～ 25% 区间上沿 | 40% |
| 中 | 蓝色 | `blue` | 25% ～ 55% 区间 | 30% |
| 良 | 红色 | `red` | 55% ～ 80% 区间 | 20% |
| 优 | 金色 | `gold` | 80% ～ 最高值 | 10% |

正式计算使用每项资质自己的最小值 `minQ` 和最大值 `maxQ`：

```text
span = maxQ - minQ
tier = serverRandomWeighted(差:40, 中:30, 良:20, 优:10)
value = randomInteger(tier.lower × span, tier.upper × span) + minQ
value = clamp(value, minQ, maxQ)
```

新区野宠首版范围建议如下（顺序为攻击 / 生命 / 速度 / 法力 / 防御）：

| 带出等级 | 攻击 | 生命 | 速度 | 法力 | 防御 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 700～1150 | 850～1200 | 850～1200 | 800～1200 | 1000～1400 |
| 5 | 750～1350 | 850～1250 | 850～1350 | 850～1350 | 1050～1500 |
| 15 | 850～1500 | 900～1400 | 900～1500 | 900～1500 | 1100～1650 |
| 25 | 950～1600 | 950～1500 | 950～1600 | 950～1600 | 1150～1800 |
| 35 | 1050～1700 | 1000～1600 | 1000～1700 | 1000～1700 | 1200～1950 |
| 45 | 1100～1800 | 1050～1700 | 1050～1800 | 1050～1800 | 1300～2050 |
| 55 | 1150～1900 | 1100～1800 | 1100～1900 | 1100～1900 | 1400～2200 |
| 65 | 1200～2000 | 1150～1900 | 1150～2000 | 1150～2000 | 1500～2350 |
| 75 | 1250～2100 | 1200～2000 | 1250～2100 | 1250～2100 | 1600～2500 |

这张表是“同带出等级的野宠通用范围”，最低值和最高值均随带出等级单调递增。具体宠物可以在范围内保留技能定位差异，例如物攻宠提高攻击上沿、法攻/治疗宠提高法力上沿、防御宠提高防御上沿，但不得突破该等级的全局最低/最高边界。历史样本低于新区最低值时，保留在证据栏，不覆盖新区配置。

五项资质分别抽取档次和数值，允许同一只野宠出现“速度优、法力良、生命中”等组合。这样能保留野宠的定位差异，也避免五项同时抽到金色导致优质宠物过度稀有。资料卡可以额外显示一个由五项归一化值加权计算的“总体资质评价”，但不再单独随机一个总档次。

带出等级只决定该宠物模板的 `minQ/maxQ` 表，不直接提高档次概率；五项资质范围按等级单调递增，但各项增长速度可以不同，仍可能捕捉到白色差资质。当前新区正式版本固定使用上述概率和范围；后续若调整必须提升规则版本，不改动已有实例。

实例必须持久化每项出生资质、每项档次、颜色 token、带出等级、上下限版本和随机结果流水。查看菜单只读取已保存结果，不能刷新或重复随机；资质提取器读取实际数值，不读取颜色或档次。红色/加成资质、资质宝石和装备资质使用独立来源颜色，不覆盖出生资质颜色。

推荐展示：资质数值按单项档次着色；宠物名称和头像不因单项颜色改变；若显示总体评价，则只显示“差/中/良/优”文字，不用总体颜色覆盖五项数值颜色。

### 6.1C 野宠捕捉与实例规则

野宠使用道具“宠物精灵球”捕捉。每只进入捕捉流程的野宠由服务端随机生成6～12点抵抗值；玩家每使用1个宠物精灵球，消耗该道具并由服务端随机降低1～3点抵抗值，最低降到0。抵抗值为0时完成捕捉并生成宠物实例；抵抗值仍大于0时只能继续削减，不能提前捕捉。

捕捉规则：

- 捕捉前先校验宠物背包空位；背包已满时无法使用宠物精灵球，不消耗道具。
- 捕捉成功后的野宠固定为1级，普通经验0，按第6.1A节计算1级属性。
- 捕捉成功时才生成并持久化五项出生资质、资质档次、颜色和唯一 `instanceId`。
- 同一种宠物允许拥有多个实例，也允许多个实例同名；所有所有权、装备、交易、培养和战斗操作必须使用 `instanceId` 区分。
- 宠物可以使用“宠物改名卡”修改显示名称；改名不改变 `instanceId`、`templateId`、资质、技能或绑定状态。
- 捕捉获得的野宠默认为未绑定；未绑定宠物允许玩家交易和放生。绑定后继续遵守不可交易规则。
- 抵抗值、每次减少值、精灵球消耗、捕捉结果和生成的 `instanceId` 必须写入服务端流水；重复请求不得重复扣球或生成第二只宠物。

### 6.2 独立修炼经验与进化流程

宠物进化不读取普通等级经验 `exp`，而是使用独立的 `evolutionTrainingExp`。

| 道具 | 作用 | 已确认结果 |
| --- | --- | --- |
| 宠物修炼册 | 使用后增加宠物修炼经验 | 每本固定增加 100 点 |
| 神品宠物进化书 | 修炼经验满后完成一次进化 | 3 点随机天赋点 + 1 点可分配天赋点 |
| 魂品宠物进化书 | 修炼经验满后完成一次进化 | 2 点随机天赋点 + 2 点可分配天赋点 |

两种进化书每次都提供 4 点天赋，区别在于随机点与可控点的比例。可分配天赋点可以投入攻击、生命、速度、法力、防御五项；进化随机点根据现有资料只随机到攻击、生命、速度和法力四项。

#### 6.2.1 修炼册经验正式方案

进化等级从 0 级到 100 级需要完成 100 次突破。每本修炼册固定提供 100 点修炼经验，总修炼需求为 25,000 点；进化书每次突破消耗 1 本，因此总共需要 100 本进化书。当前进化等级 `L`（0～99）完成本次突破所需经验为：

```text
bookTrainingExp = 100
requiredExp(L) = round(100 + L × 300 / 99)
totalExp(0 → 100) = 25,000
trainingBooks = 25,000 / 100 = 250
evolutionBooks = 100
```

关键节点示例：

| 当前进化等级 | 本次突破所需经验 |
---:|---:|
| 0 | 100 |
| 10 | 130 |
| 20 | 161 |
| 30 | 191 |
| 40 | 221 |
| 50 | 252 |
| 60 | 282 |
| 70 | 312 |
| 80 | 342 |
| 90 | 373 |
| 99 | 400 |

每级需求按四舍五入取整，100 次突破的总修炼需求正好 25,000 点，即250本修炼册。每次当前进化等级的经验达到需求后，进入 `readyToEvolve` 状态，必须再消耗1本神品或魂品进化书才能进入下一个进化等级；进化书共需要100本。经验达到本级需求后，服务端拒绝继续使用修炼册，不扣道具、不增加无效经验。若最后一本修炼册产生溢出，溢出经验保留到下一进化等级，不能被清除。

修炼经验判定：

```text
requiredExp = trainingExpTable[evolutionLevel]
trainingReady = trainingExp >= requiredExp
canUseBook = !trainingReady && evolutionLevel < maxEvolutionLevel
canEvolve = bound && trainingReady && evolutionLevel < maxEvolutionLevel
```

完整操作顺序：

1. 玩家选择宠物并使用宠物修炼册。
2. 服务端先校验当前 `trainingExp < requiredExp`；经验已满时直接返回“请使用进化书”，不消耗修炼册。
3. 服务端校验宠物所有权和修炼册数量，在事务中消耗道具并增加当前进化阶段的修炼经验。
4. 经验达到当前进化等级需求后锁定修炼册入口，等待进化书突破；最后一本修炼册产生的溢出经验进入待结转字段。
5. 玩家选择神品或魂品宠物进化书。
6. 服务端校验宠物已绑定、修炼等级为100、未达进化上限、进化书存在且状态版本一致。
7. 服务端一次性生成随机天赋落点，增加进化等级、累计可分配点和随机点；消耗进化书，将待结转溢出经验带入下一进化阶段。
8. 事务提交后返回最新宠物快照和本次天赋点结果。

当前规则没有提出进化失败概率，因此基线设计为满足条件后必定成功，随机只发生在天赋点落点上。若以后增加失败率，必须作为新的显式规则和流水结果，不能暗中加入。

随机天赋必须由服务端逐点生成并记录结果。同一个 `requestId` 重试时直接返回首次结果，不能再次随机。随机池为攻击、生命、速度、法力四项，四项采用同概率抽取。

修炼册溢出经验按进化阶段保留，不能在当前阶段经验已满后继续累积：

```text
if trainingExp < requiredExp:
  consume book and add bookTrainingExp
  if trainingExp >= requiredExp:
    readyToEvolve = true
    pendingOverflowExp = trainingExp - requiredExp
else:
  reject book use without consuming the item

on evolution book success:
  evolutionLevel += 1
  trainingExp = pendingOverflowExp
  pendingOverflowExp = 0
```

### 6.3 天赋点的四类来源

满进化、满 2 转截图的当前可见部分显示：

```text
攻击 208 + 生命 353 + 速度 199 + 法力 225 + 未分配 159 = 1144 点
```

截图未显示防御行。补上防御固定 99 点后，完整总点为 `1144 + 99 = 1243`。

#### 6.3.1 零转固定属性点

宠物未转生时，从 1 级升到 100 级，每次升级给攻击、生命、速度、法力、防御各 1 点固定属性点：

```text
fixedPointsPerStat = petLevel - 1
零转 100 级固定点 = 99 × 5 = 495
```

完成第一次转生后，这 495 点永久保留。转生后的普通升级不再每级给五项固定点，而由每 5 级的转生节点发点。

#### 6.3.2 零转可分配属性点

宠物未转生时，每次普通升级同时获得 2 点可分配属性点：

```text
preRebirthAssignable = 2 × (petLevel - 1)
零转 100 级可分配点 = 2 × 99 = 198
```

第一次转生后，这 198 点永久保留，不随转生等级重算或清空。

#### 6.3.3 进化天赋点

设神品进化次数为 `G`，魂品进化次数为 `H`：

```text
evolutionLevel = G + H
evolutionRandomPoints = 3 × G + 2 × H
evolutionAssignablePointsEarned = G + 2 × H
evolutionTotalPoints = 4 × (G + H)
```

满进化 100 次时，无论神品和魂品如何混用，进化总点恒为 400。区别只是随机点与可分配点的比例：

| 进化构成 | 随机点 | 进化可分配点 | 总点数 |
| --- | ---: | ---: | ---: |
| 100 次神品 | 300 | 100 | 400 |
| 100 次魂品 | 200 | 200 | 400 |
| 神魂混用 | `300 - H` | `100 + H` | 400 |

旧 Excel 使用 `evolutionLevel × 0.75` 平均分摊神品的 3 个随机点到攻击、生命、速度和法力，只适合理论估算。生产系统必须保存四项真实随机落点，不得用每项平均 75 点替代。防御不获得进化随机点，但可以投入可分配点。

#### 6.3.4 转生节点属性点

转生后每达到 5 级才结算一次转生可分配点。结合截图总点与 Excel 常数，累计公式为：

```text
rebirthBonus(0, level) = 0
rebirthBonus(1, level) = 10 + floor(level / 5) × 2
rebirthBonus(2, level) = 70 + floor(level / 5) × 4
```

边界结果：

| 状态 | 进入转生时 | 5～100 级节点 | 当前转生累计点 |
| --- | ---: | ---: | ---: |
| 1 转 100 级 | 10 | 20 次 × 2 = 40 | 50 |
| 2 转 1 级 | 从 50 增至 70，即新增 20 | 0 | 70 |
| 2 转 100 级 | 70 | 20 次 × 4 = 80 | 150 |

Excel 原 2 转公式使用 `70 + floor(level / 5) × 2`，满级只得到 110，导致总数少 40。满养成截图确认 2 转倍率应为 `×4`。

每次转生成功后只重置普通等级和普通经验。零转固定点、零转可分配点、进化等级、进化随机点、进化可分配点以及此前已经分配的天赋点全部保留；转生节点点数根据新的转生次数和当前等级继续累计，不得因等级回到 1 级而删除已经获得的永久点数。

### 6.4 可分配点与面板点数

可分配点公式：

```text
baseAssignable = rebirthLevel === 0
  ? 2 × (petLevel - 1)
  : 198

earnedAllocatablePoints =
  baseAssignable
  + evolutionAssignablePointsEarned
  + rebirthBonus(rebirthLevel, petLevel)

remainingPoints = earnedAllocatablePoints - sum(allocatedPoints)
```

单项面板点数：

```text
displayedPoint[stat] =
  fixedPoint[stat]
  + evolutionRandomPoint[stat]
  + allocatedPoint[stat]
```

满 100 级、进化 100、2 转 100 级的总点验算：

```text
零转固定点 495
+ 零转可分配点 198
+ 进化总点 400
+ 2 转累计点 150
= 1243
```

全部神品时，可分配总额为 `198 + 100 + 150 = 448`；全部魂品时为 `198 + 200 + 150 = 548`。这些可分配点可以投入五项属性。两种路线最终总点都为 1243，仅可控程度不同。

服务端约束：

```text
allocated.hp
+ allocated.attack
+ allocated.speed
+ allocated.mana
+ allocated.defense
<= earnedAllocatablePoints
```

- 五项已分配点数必须是非负整数，拒绝其他未知加点键。
- 随机天赋点不可进入未分配池，也不可通过客户端改写落点。
- 转生节点只在跨过 5 的倍数时发放一次，重复经验请求不得重复发点。
- 洗点使用“宠物洗点卡”，每次重置消耗 1 张，只重置玩家手动分配点；零转固定点和进化随机点不可重塑。
- 任一属性达到统一上限后禁止继续投入该属性点，客户端应在确认前提示“已达上限”。
- 降级、重置或规则迁移不得产生已分配点数大于已获得点数的非法状态。

### 7.1 换算常量

### 7.2 生命、攻击、速度和法力

定义：

```text
Qb = 基础资质显示池（宠物原始基础资质 + 资质卡）
Qr = 加成资质显示池（资质宝石镶嵌形成的红色/加成资质）
QbNative = 宠物原始基础资质
QrNative = 宠物培养获得的红色/加成资质
C  = 对应属性换算常量
M  = 宠物资质成长比例 `petQualificationScale`
P0 = 宠物 1 级自然成长单位，固定为 1
Pb = 零转升级永久获得的对应属性固定点数
Pa = 玩家分配到对应属性的点数 + 进化随机落到对应属性的天赋点
B  = 贴纸、圣技、天赋、神器等百分比加成之和
```

参考公式：

```text
weightedQualification = Qb × 1.1 + Qr × 1.2
birthStat = QbNative × 1.1 ÷ C × M × P0
pointGrowthStat = weightedQualification ÷ C × (Pb + Pa)
growthStat = birthStat + pointGrowthStat
growthStatWithPercent = growthStat × (1 + B)
panelStat = round(growthStatWithPercent)
```

各中间计算保留内部精度，只有最终面板展示值执行取整；战斗快照使用与面板相同的最终整数值，不在客户端再次取整。

资质卡直接加入基础资质显示池，按基础资质的 `1.1` 权重参与普通属性点换算；资质宝石镶嵌提升显示为红色/加成资质，并按加成资质的 `1.2` 权重参与普通属性点换算。虽然菜单显示为两个合计池，实例仍必须保存 `native/card/red/gemCard` 来源明细，其中 `gemCard` 是红色/加成值的来源记录，不得在合计时重复计算。1级隐藏单位只读取宠物原始基础资质 `QbNative`，不读取后续卡片和红色资质。

### 7.3 防御与潜力

已确认的两个参照点：

```text
潜力 10,000 -> 防御有效资质 × 0.18 的额外防御
潜力 15,000 -> 防御有效资质 × 0.27 的额外防御
```

两点对应的线性参考系数：

```text
potentialCoefficient = potential × 0.000018
```

参考防御公式：

```text
weightedDefenseQualification = defenseBasePool × 1.1 + defenseBonusPool × 1.2
birthDefense = defenseBaseNative × 1.1 ÷ 277.77 × M
defenseFromPoints = weightedDefenseQualification ÷ 277.77 × defensePointUnits
totalDefenseQualification = defenseBaseNative + defenseCard + defenseRed
defenseFromPotential = totalDefenseQualification × min(potential, 15000) × 0.000018
defensePercentMultiplier = 1 + artifactDefenseRate + talentDefenseRate + stickerDefenseRate
growthDefense = floor(birthDefense × defensePercentMultiplier)
              + floor(defenseFromPoints × defensePercentMultiplier)
              + floor(defenseFromPotential × defensePercentMultiplier)
```

这里的 `totalDefenseQualification`（防御总资质）只表示防御单项的所有资质来源之和，不是攻击、生命、速度、法力、防御五项资质合计。其正式定义为：

```text
防御总资质 = 基础防御资质池（原始防御资质 + 资质卡防御资质）
           + 红色/加成防御资质池（资质宝石镶嵌提升）
```

资质卡直接加入基础资质池，资质宝石卡的数值通过镶嵌形成红色/加成资质池；`gemCard` 只保留为来源明细，不在总和中重复计算。两个资质池在潜力公式中直接相加，不应用普通属性点公式的 `1.1/1.2` 权重。潜力防御可以受到法宝、天赋和贴纸的防御百分比加成；这些百分比按加法合并后形成统一倍率。

宠物1级默认亲密度为100、潜力为15。零转普通升级时每次获得亲密度100、潜力150；转生后亲密度和潜力沿用当前值，不因重新从1级升级重复获得，潜力最高15000。达到潜力上限后不再增加。潜力从10000提升至15000的额外来源以及潜力能否重置仍待确认。

满养成截图的当前可见区域没有显示防御行，但防御可以主动加点。防御点数由零转固定点和玩家分配点组成，不获得进化随机点：

```text
defensePointUnits = fixedDefensePoint + allocatedPoints.defense
```

1级隐藏单位已单独进入 `birthDefense`，不能再次计入 `defensePointUnits`。满级固定防御点仍为99；截图中四项与未分配点合计1144，再加防御99，完整可养成点总数仍为1243。

用户确认样例：基础防御资质0、红色防御资质84000、潜力10000、五防贴112%、天赋30%、法宝10%，防御点为99+408=507：

```text
防御百分比倍率 = 1 + 1.12 + 0.30 + 0.10 = 2.52
潜力防御 = floor((0 + 84000) × 0.18 × 2.52) = 38102
属性点防御 = floor((0 × 1.1 + 84000 × 1.2) ÷ 277.77 × 507 × 2.52) = 463642
合计防御 = 38102 + 463642 = 501744
```

仍待确认：潜力从 10,000 提升到 15,000 的额外来源，以及潜力能否重置。1级初始亲密度/潜力、升级增量、潜力上限和防御总资质口径已经确定。

## 9. 统一属性结算管线

建议服务端按固定顺序计算：

```text
1. 读取宠物模板与实例成长状态
2. 校验等级、进化、转生、资质、潜力和已分配点数
3. 计算资质与属性点产生的成长属性
4. 计算防御潜力
5. 应用成长类百分比来源
6. 应用宠物装备的固定属性和百分比属性
7. 应用永久被动技能属性
8. 生成未截断 rawStats
9. 对五项核心属性应用人物、佣兵、宠物共用的 STAT_LIMITS
10. 生成 effectiveStats 和 statBreakdown
```

推荐快照结构：

```json
{
  "rawStats": {
    "hp": 5100000,
    "attack": 480000,
    "defense": 320000,
    "speed": 98000,
    "mana": 103000
  },
  "effectiveStats": {
    "hp": 5000000,
    "attack": 480000,
    "defense": 320000,
    "speed": 98000,
    "mana": 100000
  },
  "cappedStats": ["hp", "mana"],

    "qualification": {},
    "allocatedPoints": {},
    "potential": {},
    "percentBonuses": {},
    "equipment": {},
    "passiveSkills": {}
  },

}
```

固定装备属性究竟在成长百分比之前还是之后、被动技能是否可以突破宠物上限，资料没有完全说明。建议默认采用“固定属性先相加、对应百分比再相乘、最终统一截断”的现有装备结算习惯，并把顺序写入公式版本；正式数值确认后不得静默修改旧版本。

## 10. 取整、边界与防作弊

建议规则：

- 中间计算使用有限数值并保留小数。
- 最终可见属性统一 `Math.round`；若需要完全复刻原版向下取整，可通过公式版本切换。
- 五项核心属性不得为负数，生命和攻击至少为 1。
- 所有输入必须通过 `Number.isSafeInteger` 或有限数值校验。
- 客户端提交的“计算后属性”一律忽略，只接收操作目标和分配方案。
- 服务端拒绝未知属性键、负分配、超额分配、重复技能槽和不存在的装备实例。
- 战斗开始时生成不可变宠物属性快照，战斗中成长操作只影响下一场战斗。

### 11.1 新区绝世宠模板资质规则

绝世宠的五项模板资质总和以 20,000 左右为基准，允许随机上浮最多 5%。设计工具从 `[20000, 21000]` 中选择一个不规则整数作为该宠物的目标总和，不把 20,000 当成固定总值。

分配规则：

- 根据天生技能公式建立五项权重；参与伤害、治疗、护盾或生存公式的资质获得较高权重。
- 五项数值在权重结果上加入小幅随机扰动，再分配取整尾差，避免出现 4000、4500 等刻意的整百、整千组合。
- 最高资质与最低资质的差距不超过最低资质的 50%，校验式为 `maxQualification <= minQualification × 1.5`。
- 总和、单项随机尾数和技能权重必须同时满足；不能为了凑总和把某一项变成明显废属性。
- 随机只发生在模板设计或批量生成阶段。模板一旦审核入库，绝世宠和其他非野宠一样使用固定资质；捕捉、召唤或创建实例时不得重新随机。
- 原图资质与新区设计资质分栏保存。原图属于证据数据，新区值属于运营模板，二者不得互相覆盖。

示例：天空之王.赛特的技能以速度和法力为主，可使用攻击 3473 / 生命 3586 / 速度 4719 / 法力 4837 / 防御 3672，总和 20,287。该示例只说明生成方式，最终批量设计时仍需为每只绝世宠独立取样并复核技能权重。

#### 天生技能实现约束

- “全体必中”“必中”“无视技抗”是不同标签，不能互相替代；必中只跳过命中/闪避判定，无视技抗只影响技抗减免。
- 浮动伤害必须由服务端确定随机结果并写入战斗日志；同一战斗重放不得重新抽取。
- “可叠加”“不可叠加”“受到攻击解除”“与嗜血冲突”“无法补血转扣血”必须作为状态元数据配置。
- 技能造成的生命、精力、命中、闪避、抗性和逆抗变化分别记入对应字段，不得合并成一个伤害值。
- 非战斗技能只在宠物被主人带出且满足生活技能条件时生效，不应进入普通战斗伤害结算。

#### 技能说明查看文案、排版与颜色

宠物资料卡中的“天生技能说明”是技能查看功能的权威文案源。技能配置不能只有公式字段，也不能在菜单打开时临时拼接一句说明；每个技能必须同时保存可搜索/无障碍读取的完整纯文本，以及可以直接渲染的分行彩色结构。

统一排版顺序：

1. 技能标题单独一行。
2. 类型标签、目标范围和消耗一行。
3. 伤害、治疗或强化公式一行；复合公式过长时按运算段换行，不拆开数字与单位。
4. 状态名称、威力、命中率和持续回合一行或多行。
5. 叠加、刷新、解除、冲突和特殊限制放在末行。
6. 原图中的剧情/风味文字保存为可选 `flavorLines`，排在机制说明之后，不与公式混写。

颜色标记与现有 `skill-library` 保持一致：

| `color` | 用途 |
| --- | --- |
| `gold` | 技能标题、品级词、状态名称 |
| 空字符串 | 默认白色正文、类型标签、连接词和标点 |
| `red` | 精力/生命消耗、自损、危险提示和禁止条件 |
| `green` | 伤害/治疗公式、概率、回合数、属性增减和关键机制数值 |

```json

  "heroRuneSkill": "common_passive_xxx",

  "innateSkill": "pet_active_xxx"

```

宠物法宝技能不写入宠物本体的永久技能槽。法宝实例保存最多 3 个已打入的宠物技能卡，服务端根据宠物当前穿戴的法宝动态生成 `artifactSkills`；穿上时自动获得，卸下、换装或法宝失效时立即移除。战斗快照只读取本次快照生成时仍有效的法宝技能。

### 12.1 主动神符与英雄神符

主动神符和英雄神符都是有独立实例 ID 的道具，不是宠物技能卡的别名。学习分为两步：

1. 玩家选择神符道具，再选择一张兼容的宠物技能卡打入神符。
2. 玩家对目标宠物使用已打入技能卡的神符，宠物才可学习或装备对应神符技能。

主动神符只能打入主动宠物技能卡；英雄神符可打入主动或被动宠物技能卡。技能卡成功打入主动神符或英雄神符后，原技能卡立即消耗，已经打入的技能卡不能拆除或替换。已打入技能的神符用于宠物学习后，神符道具本身也消耗。服务端必须校验神符实例、技能卡实例、所有权、兼容类型、重复技能类别和宠物目标，客户端不得直接提交技能 ID。

### 12.2 普通技能学习与野宠资料归档

#### 野宠初始技能归档

野宠的 3 个初始普通技能已经在《宠物资料与资质合成汇总》20.2A 中随机抽样一次并固定写入每张资料卡。该随机只属于资料编制阶段，游戏运行时不得在捕捉、生成、查看菜单、叫出或收回时重新抽取。实例创建时直接复制对应模板的 3 个技能 ID 到 `ordinarySkills`；客户端不能提交或改写技能结果。

当前归档池版本为 `pet_wild_initial_passive_b_v1`，包含 17 个 B 级被动技能，仅用于资料编制和后续补档。若补充新野宠，先在开发文档中完成一次无放回抽样并固化组合，再进入模板配置。

#### 初始无普通技、可扩展 3 个技能的宠物

资料面板中“普通技：无（最多可用技能卡扩展 3 个）”的五只宠物，已从项目 `common.js` 宠物可用 A 级被动技能池中各随机抽样一次并固定归档：

| 宠物 | 固定普通技能 |
| --- | --- |
| 野猪王 | 坚韧A、强力A、嗜血A |
| 狮子王 | 涅槃A、强力A、警惕天性A |
| 陆行鸟.莫古力 | 厚甲A、刺甲A、致命A |
| 狐铃铛 | 结界A、涅槃A、警惕天性A |
| 灰大狼.巴嘎 | 强壮A、反噬A、坚韧A |

这些组合是文档固定配置，不在宠物生成、查看或战斗时重新随机；技能卡后续学习仍遵循普通技能槽随机命中和覆盖规则。

#### 其他缺失普通技能的宠物

《宠物资料与资质合成汇总》中原本缺少普通技能的绝世宠和名称已确认宠物，均根据已知天生技能公式归为物攻、法攻、速度、混合或辅助类型，再从项目现有A级宠物被动技能池无放回选择3个并固定归档。详细组合以该资料文档的宠物卡为准；该选择仅发生在资料编制阶段，宠物实例生成时直接复制模板结果，不得在运行时重新随机。后续若取得原版普通技能的可靠证据，由策划确认是否替换当前设计组合并提升模板版本。

#### 技能卡随机学习

三个普通技能槽可直接使用宠物技能卡学习，不需要先经过神符或宠物法宝。每次学习由服务端在 3 个普通技能槽中随机选定一个目标槽位，因此可能写入空槽，也可能覆盖任意一个已有普通技能；客户端不得指定目标槽。若技能类别已存在于宠物其他技能槽，服务端拒绝学习或替换，保证一类技能只存在一个。

确认框必须明确显示宠物头像、宠物名字、技能卡和提示“将随机写入 3 个普通技能槽之一，可能覆盖已有技能”。确认前不得预告随机槽位。成功结果显示本次命中的槽位、新技能，以及被覆盖的旧技能；命中空槽时显示“新增技能”。取消操作不消耗技能卡。

服务端在同一事务内锁定宠物与技能卡、选择随机槽位、记录旧/新技能、消耗卡片、增加宠物版本并写入流水。相同 `requestId` 重试必须返回第一次的槽位和结果，不得再次随机，也不得重复消耗。

### 12.3 宠物法宝技能

宠物技能卡需要先打入具体宠物法宝实例的技能槽。宠物穿上该法宝时自动获得法宝内全部有效技能，卸下法宝后自动失去，不再执行一次“宠物学习”操作，也不把技能复制进宠物永久技能数据。

法宝技能操作必须分别校验技能卡与法宝的所有权、技能类型、法宝槽位是否已解锁、法宝是否处于可修改状态，以及重复技能规则。法宝技能卡允许拆除和替换：拆除时移除该技能，替换时旧技能立即消失；原技能卡不返还。技能卡打入、替换或拆除时需要标准确认框，展示法宝原图标、原品质文字颜色、目标槽、旧技能、新技能和材料去向。

技能操作必须校验：

- 技能存在且允许宠物使用。
- 技能类型符合槽位限制。
- 槽位已解锁。
- 技能卡属于玩家且在事务提交后才消耗。
- 同一技能或同一技能类别不得重复存在，服务端必须在所有技能槽之间统一校验。
- 换技能前显示旧技能、新技能和不可逆消耗确认。

主动和被动技能卡的命名、字段及完整目录继续引用关联文档，战斗效果只读取 `systems/skill/pet.js` 与 `systems/skill/common.js`。

## 13. 宠物装备模型

### 13.1 神器锻造参考值

| 宠物法宝类型 | 普通锻造每 +1 | 圣锻每 +1 |
| --- | ---: | ---: |
| 宠物法宝（速度） | 速度 +6 | 速度 +1% |
| 宠物法宝（法力） | 法力 +9 | 法力 +1% |
| 宠物法宝（攻击） | 攻击 +50 | 攻击 +1% |
| 宠物法宝（防御） | 防御 +50 | 防御 +1% |
| 宠物法宝（生命） | 生命 +500 | 生命 +1% |

宠物法宝普通锻造达到 +15 后具备完整技能扩展资格。圣锻、打孔和注魔均为 100% 成功，材料按 1:1 消耗。普通锻造使用“锻造宝石”，属于独立的普通锻造体系；圣锻使用“宠物饰品强化石”，不能混用两种材料。普通锻造的成功率、属性增量和失败规则仍待配置。

宠物饰品自带 1 个技能槽；使用宠物饰品强化石进行圣锻达到 +5 时解锁第 2 个技能槽，达到 +10 时解锁第 3 个技能槽，最多 3 个。使用锻造宝石进行普通锻造或普通体系圣锻，不能解锁第 2、3 个额外技能槽。普通锻造的成功率、属性增量和失败规则仍待配置。

宠物法宝本体是可重复穿戴的装备实例，不会因宠物学习或技能覆盖而消耗。法宝技能槽中的技能卡可用另一张技能卡覆盖，旧技能立即消失；更换另一件宠物法宝时，宠物的法宝技能随当前装备动态切换。

### 13.2 守护戒指

参考规则：

- 初始守护等级 50，对应 5% 技能伤害减免。
- 强化 +1，守护等级 +20，约增加 2% 减免。
- 守护等级最高 500，对应 50% 减免。
- 对无视防御技能和普通攻击只发挥一半效果。
- 治疗削减直接引用项目现有守护戒指公式和版本配置，宠物模块不另行复制或推导公式。

守护戒指效果属于伤害结算修正，不应转换成面板防御。战斗日志应记录减免前伤害、守护减免、治疗削减和最终结果；公式版本沿用项目现有配置。

### 13.3 腰带与披风

| 装备 | 插槽与效果 |
| --- | --- |
| 银质宠物腰带 | 2 个元素孔；镶嵌宝石属性上下限均提升 10% |
| 金质宠物腰带 | 3 个元素孔；镶嵌宝石属性上下限均提升 20% |

| 圣品宠物披风使用宠物披风打孔器后 | 5 个资质孔 + 3 个元素孔 |

圣品宠物披风孔位固定为资质孔一至四、元素孔一至二；打孔后新增资质孔五和元素孔三。银质宠物腰带固定为元素孔一至二，金质宠物腰带固定为元素孔一至三。每个孔位最多镶嵌一颗对应类型宝石。

补充物品截图显示 `金质宠物腰带（0/3）`，并且背包中可以同时存在多个独立腰带实例，进一步确认黄金腰带具有 3 个实例孔位。

### 13.4 资质提取器与资质宝石

已确认流程：

1. 玩家对来源宠物使用唯一档位的宠物资质提取器。
2. 系统按 50% 比例读取来源宠物的总资质，并按五项资质比例生成对应宝石数值。
3. 提取结果生成一颗携带五项资质的宠物资质宝石；宝石携带的五项资质总和等于来源宠物可提取总资质的 50%。
4. 玩家把资质宝石镶嵌给新的宠物。
5. 新宠物将宝石数值计入 `qualifications.gemCard`，再由统一属性公式结算。

资质宝石增加的是资质，不是直接增加最终生命、攻击、防御、速度和法力。宝石实例还可以限制具体宠物模板，例如“多头蛇怪资质宝石”只允许多头蛇怪使用。

必须防止重复复制资质：提取时直接消耗来源宠物，来源宠物及其全部资质、装备和培养状态一并失效；已经来自镶嵌宝石的资质不得再次参与提取。提取、宠物消耗和宝石生成必须在同一事务中完成。

来源宠物已绑定时，产出的资质宝石应继承不可交易状态，避免通过提取把绑定资产洗成可交易道具。

## 14. 服务端权威与接口边界

现有宠物召唤、拥有状态、请求幂等和资产流水应继续沿用 `pet_asset` 权威链路。新成长操作必须具有相同安全等级。

建议接口边界：

| 操作 | 建议路由 | 核心校验 |
| --- | --- | --- |
| 查看宠物详情 | `GET /api/pets/:instanceId` | 所有权与可见范围 |
| 绑定宠物 | `POST /api/pets/:instanceId/bind` | 未绑定、未交易、版本一致 |
| 使用宠物修炼册 | `POST /api/pets/:instanceId/evolution-training` | 修炼册数量、经验边界、版本一致 |
| 分配属性点 | `POST /api/pets/:instanceId/allocate-points` | 点数合法、总额未超限 |
| 重置属性点 | `POST /api/pets/:instanceId/reset-points` | 消耗与重置规则 |
| 进化 | `POST /api/pets/:instanceId/evolve` | 已绑定、修炼经验、进化书类型、等级上限 |
| 转生 | `POST /api/pets/:instanceId/rebirth` | 等级恰当、转生上限、材料 |
| 神符打入技能卡 | `POST /api/pet-runes/:runeInstanceId/socket-skill` | 神符与卡片所有权、类型、槽位和版本 |
| 使用神符学习技能 | `POST /api/pets/:instanceId/rune-skills` | 已打入技能的神符、目标宠物、技能适用性 |
| 普通技能随机学习 | `POST /api/pets/:instanceId/ordinary-skills/random-learn` | 卡片所有权、3 个普通槽、服务端随机和版本 |
| 法宝打入技能卡 | `POST /api/pet-artifacts/:artifactInstanceId/socket-skill` | 法宝与卡片所有权、槽位解锁、类型和版本 |
| 穿戴/卸下装备 | `POST /api/pets/:instanceId/equipment` | 装备所有权、类型和并发版本 |
| 提取宠物资质 | `POST /api/pets/:instanceId/extract-qualifications` | 提取器、来源资质、绑定、出战与版本状态 |
| 镶嵌资质宝石 | `POST /api/pets/:instanceId/qualification-gems` | 宝石所有权、模板限制、孔位与版本状态 |

每个写请求至少携带：

```json
{
  "requestId": "uuid",
  "expectedVersion": 12,
  "evolutionBookType": "divine"
}
```

`evolutionBookType` 仅在进化接口使用，候选值为 `divine`（神品）和 `soul`（魂品）。使用宠物修炼册的接口应提交消耗数量，服务端根据道具配置计算经验，客户端不得直接提交要增加的经验值。

服务端在同一事务中完成：读取权威实例、校验版本、校验并扣除消耗、生成并记录随机结果、修改宠物状态、写资产流水、增加版本号、返回最新宠物快照。重复 `requestId` 返回第一次提交结果，不得重复扣除或重新随机。

建议流水原因：

- `pet_bind`
- `pet_evolution_training_gain`
- `pet_evolve_divine`
- `pet_evolve_soul`
- `pet_rebirth`
- `pet_allocate_points`
- `pet_reset_points`

## 15. 持久化设计与迁移

### 15.1 当前状态

当前 `server/pet-progress.js` 每只宠物只保存：

```json
{
  "level": 1,
  "exp": 0
}
```

`systems/pet/index.js` 使用等级 1 到 100 的临时线性属性，`server/stats.js::statsForPetRow` 再叠加宠物装备与技能。该结构不能可靠承载绑定、交易、同种多实例、资质、进化、转生和并发修改。

### 15.2 推荐表结构

建议新增规范化宠物实例表，避免继续扩大 `players.pet_progress_json`：

```sql
CREATE TABLE pet_instances (
  instance_id TEXT PRIMARY KEY,
  template_id INTEGER NOT NULL,
  owner_account TEXT NOT NULL,
  bound INTEGER NOT NULL DEFAULT 0,
  level INTEGER NOT NULL DEFAULT 1,
  exp INTEGER NOT NULL DEFAULT 0,
  evolution_level INTEGER NOT NULL DEFAULT 0,
  evolution_training_exp INTEGER NOT NULL DEFAULT 0,
  evolution_assignable_points INTEGER NOT NULL DEFAULT 0,
  evolution_random_points_json TEXT NOT NULL DEFAULT '{}',
  rebirth_level INTEGER NOT NULL DEFAULT 0,
  potential INTEGER NOT NULL DEFAULT 0,
  allocated_points_json TEXT NOT NULL DEFAULT '{}',
  qualifications_json TEXT NOT NULL DEFAULT '{}',
  stickers_json TEXT NOT NULL DEFAULT '[]',
  talent_effects_json TEXT NOT NULL DEFAULT '[]',
  skill_slots_json TEXT NOT NULL DEFAULT '{}',
  state_version INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

装备实例仍由现有装备存储维护，只保存 `equippedBy = pet instanceId`，避免把同一装备复制进两个状态源。

### 15.3 旧宠物清理与新系统启用

旧宠物不迁移到新宠物实例，全部以新宠物系统为准：

1. 上线新系统前停止旧 `owned_pets_json` 和 `pet_progress_json` 的宠物写入。
2. 清除旧宠物拥有、等级、经验和出战数据，不为旧宠物生成新 `instanceId`。
3. 新系统启用后，玩家只能通过新系统规定的捕捉、召唤或发放入口获得宠物实例。
4. 所有新接口只接受新系统生成的 `instanceId`；不得保留旧模板 ID 写入兼容分支。
5. 清理旧协议、旧线性成长和旧宠物菜单兼容代码，避免新旧状态并存。

执行清理前应保留只读备份和数量核对报告，用于异常追查，但备份不得重新导入新宠物系统。

## 16. 客户端菜单与预览

宠物详情建议拆分为以下视图：

- 基础：头像、名字、等级、经验、进化、转生、绑定状态。
- 修炼：独立修炼经验条、当前级需求、修炼册使用入口和进化书选择。
- 属性：有效属性、原始属性、属性上限和来源明细。
- 加点：随机天赋落点、已获得可分配点、已使用点、剩余点及加点前后预览。
- 资质：基础、红色、卡片、宝石、潜力和换算结果。
- 技能：按槽位展示，不显示为无归属的技能数组。
- 装备：神器、守护戒指、腰带、披风、孔位和宝石。

关键交互：

- 未绑定宠物的进化按钮显示锁定原因“绑定后可进化”。
- 修炼经验未满时显示当前值和目标值，不允许使用进化书。
- 修炼经验满后显示“选择进化方式”，分别列出神品的“随机 3 / 可分配 1”和魂品的“随机 2 / 可分配 2”。
- 进化确认框只展示可能获得的点数结构，不提前展示随机属性落点。
- 进化成功框显示宠物头像、名字、进化等级变化、本次随机落点和新增可分配点。
- 100 级以下的转生按钮显示“达到 100 级后可转生”。
- 属性加点在确认前显示五项属性变化、剩余点数和上限溢出。
- 达到上限的属性继续投入点数时必须明确提示无实际收益；是否允许投入由玩法规则确认。
- 绑定、转生、进化、洗点、技能替换均使用标准确认对话框。
- 普通技能卡学习不提供槽位选择；确认框必须警告随机覆盖，结果框再公布命中槽位和被覆盖技能。
- 主动/英雄神符菜单按“选择神符 -> 选择兼容技能卡 -> 打入确认 -> 选择宠物 -> 学习确认”分段，禁止选择未打入技能卡的空神符学习。
- 宠物法宝菜单按“选择法宝 -> 选择已解锁技能槽 -> 选择技能卡 -> 打入/替换确认”处理；宠物换装预览同时列出将获得和将失去的法宝技能。
- 召唤和收回沿用已统一的头像、宠物名字和标准结果对话框。
- 成功操作关闭当前确认结果流程，不应无条件再次弹出上一级宠物菜单。

客户端显示的计算预览必须来自服务端 `preview` 接口或与响应同版本的只读公式包；提交后仍以服务端返回快照为准。

## 19. 最小测试方案

本系统实现时按阶段做定向测试，不需要每轮执行全量回归。

必须覆盖：

- 五项换算常量与公式版本。
- 0/1/2 转各等级边界的可分配点数。
- 零转每次升级五项固定点各 +1、可分配点 +2，100 级合计 693 点。
- 1 转 5 级节点增加 2 点，2 转 5 级节点按累计公式增加 4 点。
- 满 100 级、进化 100、2 转 100 级总点必须等于 1243。
- 五项面板点数与未分配点之和恒等于已获得总点，防御允许主动加点。
- 99 级不可转生、100 级可转生。
- 未转生、1 转、2 转分别读取各自的 1～100 级普通经验曲线，2 转 100 级后拒绝升级和转生。
- 1 个宠物转生宝石按 75% 服务端判定，2 个宠物转生宝石必定成功，其他数量被拒绝；1个判定失败时材料仍消耗。
- 转生成功后等级回到 1 级、普通经验清零，进化等级和全部天赋点保持不变。
- 转生请求重试不重复随机或扣除宠物转生宝石，2 转后拒绝再次转生。
- 未绑定不可进化、绑定后可进化、绑定后不可交易。
- 普通等级经验与修炼经验完全隔离。
- 修炼经验未满不可消耗进化书，经验满后只扣除一次。
- 神品进化固定产生 3 点随机点和 1 点可分配点。
- 魂品进化固定产生 2 点随机点和 2 点可分配点。
- 神品、魂品混合进化后累计点数与进化历史一致。
- 重复进化请求不重复消耗进化书，也不重新随机天赋落点。
- 重复绑定、重复请求和双客户端版本冲突。
- 属性点负数、超额、未知字段和溢出输入。
- 1 级亲密度100、潜力15，零转升级分别增加100和150；洗点卡每次消耗1张，达到上限后拒绝继续加点。
- 防御潜力读取防御单项全部资质来源，且不混入其他四项资质。
- 资质提取器只有一个档位，按50%提取并消耗来源宠物；已镶嵌宝石资质不得再次提取。
- 属性刚好等于上限和超过上限。
- 技能类型与槽位不匹配、未解锁神器槽。
- 主动神符拒绝非主动技能卡，空神符不能用于宠物学习。
- 普通技能学习只能由服务端在 3 个槽中随机，重复请求不重复扣卡、不改变首次随机槽位。
- 普通技能随机命中空槽与覆盖已有槽时，结果和流水中的旧/新技能均正确。
- 同一技能类别重复学习、神符学习或法宝穿戴时均被服务端拒绝。
- 法宝普通锻造 +15、宠物饰品强化石圣锻 +5/+10 的 1/2/3 槽解锁，锻造宝石不能解锁后两槽。
- 法宝穿戴后自动获得其技能，卸下或更换后立即移除旧法宝技能且不污染宠物永久技能槽。
- 同一宠物法宝技能在菜单预览、持久化状态和战斗快照中来源一致。
- 成熟宠物 12 个技能槽的类型、顺序和战斗快照一致。
- 资质提取比例、五项宝石结果和镶嵌后的属性预览一致。
- 已镶嵌宝石资质不能被循环提取，重复请求不重复生成宝石。
- 绑定宠物提取结果不能变成可交易资产。
- 装备、卸装和换装后的属性预览一致性。
- 战斗快照、竞技镜像和断线恢复的一致性。
- 旧宠物清理后不可通过旧接口恢复、出战或写入新实例表。

完整实现后再执行一次宠物模块核心冒烟；只有共享战斗协议、数据库迁移或上线验证时才需要扩大回归范围。

## 21. 完成标准

以下条件全部满足后，宠物成长模块才算完成：

- 宠物拥有独立实例，绑定和交易限制无法绕过。
- 100 级转生与绑定后进化均由服务端权威校验。
- 宠物普通经验与修炼经验完全隔离，修炼册和两类进化书消耗均可追溯。
- 神品、魂品及混合进化产生的随机点与可分配点长期累计准确，重试不会重新随机。
- 人物、佣兵、宠物全部使用同一套五项最终属性上限。
- 五项属性由同一个版本化计算器生成，所有战斗入口结果一致。
- 原始属性、有效属性、上限和来源明细可解释。
- 属性点、资质、潜力、技能槽和装备均可持久化且支持并发版本控制。
- 资质提取和镶嵌不会复制资产，五项资质来源和绑定继承均可追溯。
- 所有材料消耗具有事务、幂等、流水和异常恢复能力。
- 旧宠物数据按新系统启用规则完成一次性清理，旧线性成长与兼容代码被删除。
- 客户端对绑定、进化、转生、加点、技能和装备操作都有明确预览与标准对话框。
- 定向边界测试和宠物核心冒烟通过。
