# 组队与组队战斗 V2 重做计划

## 1. 文档目的

重做组队、队伍跟随切图、组队 PVE、组队 PVP、断线恢复和奖励交付链路，解决当前多份状态、客户端直接修改 roster、`peerId` 时序依赖和联网战斗运行时职责过重造成的长期不稳定。

本计划基于当前仓库重新编写。当前未发现独立的服务端地图位置/传送票据 runtime，因此服务端权威切图属于本次重做范围，不能假设已有实现。

## 2. 重做目标

1. 队伍身份、成员关系、队长权限和参战名单全部由服务端权威状态决定。
2. `account` 是稳定身份；`peerId` 只表示当前 WebSocket 连接地址。
3. 队长切图后由服务端创建一次队伍传送任务，每名成员使用独立票据完成切图。
4. 组队战斗从建局、锁定名单、收集选择、回合结算、奖励到结束只有一个服务端会话所有者。
5. 断线、重连、重复包、乱序包、超时和连续战斗均能收敛。
6. `app.js`、`server.js` 只保留初始化、依赖注入和路由接线。
7. 分阶段迁移，每阶段独立测试、提交和回滚，不直接一次性替换全部旧功能。

## 3. 非目标

本轮不重写：

- `战斗/engine.js` 的伤害、技能、状态和回合公式。
- 现有战斗画布、动画和菜单视觉设计。
- 地图文件格式与地图编辑器。
- 无协议关联的单机 NPC 战斗。
- Express、Nest、React 等大型框架迁移。

## 4. 当前基线与问题

### 4.1 当前体量

```text
app.js                  13,867 行
server.js                6,289 行
队伍/runtime.js            222 行
队伍/server.js             442 行
联网战斗/runtime.js       1,167 行
```

### 4.2 双份队伍逻辑

- `队伍/server.js` 已维护邀请和 canonical 成员关系。
- `server.js` 仍保留 `teamAccepted`、`teamUpdate`、`teamLeave`、`teamDisband` 的旧元数据处理。
- `app.js` 仍会直接拼装和广播成员列表。
- 同一 roster 同时存在客户端状态、入口 socket meta 和队伍 runtime 三个来源。

### 4.3 协议缺少版本与顺序

- `teamAccepted`、`teamUpdate`、`teamLeave`、`teamDisband` 的职责重叠。
- 没有 `teamId` 和单调递增 `revision`，客户端无法可靠识别旧快照。
- 指令没有统一 `requestId`，重复点击和网络重试无法稳定幂等。
- 名称、账号、旧 `peerId` 都可能被用于匹配同一个玩家。

### 4.4 跟随切图不具备服务端事务

- 当前地图系统只有管理和清单模块，没有独立 canonical 位置与传送票据 runtime。
- 队伍跟随主要依赖客户端观察队长状态并自行切图。
- 服务端无法回答某次队伍切图中谁已到达、谁失败、谁需要重试。
- 客户端上报地图和坐标容易与队伍、遭遇和战斗校验产生时序分叉。

### 4.5 联网战斗职责过多

`联网战斗/runtime.js` 同时负责：

- PVE/PVP 建局
- 队伍展开
- 玩家、宠物和佣兵重建
- 技能合法性过滤
- 选择收集和超时
- 回合结算
- 断线投递
- 结束和奖励

修改其中一个时序分支容易影响其他战斗类型。

## 5. 设计原则

### 5.1 单一身份

- 权限与成员资格只认 `{ account, serverId, channelId }`。
- `peerId` 仅用于向账号当前连接发送消息。
- 显示名只用于 UI，不参与权限、成员关系或单位 ownership 判断。

### 5.2 单一状态所有者

- `TeamRuntime` 是队伍关系唯一写入者。
- `TeamTravelRuntime` 是队伍切图任务唯一写入者。
- `OnlineBattleSession` 是在线战斗唯一写入者。
- 客户端只提交意图并渲染快照，不直接扩展、删除或重排服务端 roster。

### 5.3 版本化快照

- 每个队伍有不可预测的 `teamId`。
- 每次权威变更令 `revision += 1`。
- 客户端只应用更新 revision；重复或旧快照直接忽略。

### 5.4 幂等与可恢复

- 每条写指令包含 `requestId`。
- 服务端短期缓存账号与 requestId 的结果。
- 切图、选择、结束和领奖都允许安全重试，不能重复生效。

## 8. V2 协议

### 8.1 通用信封

```json
{
  "type": "team.v2.invite",
  "requestId": "random-id",
  "payload": {}
}
```

服务端事件统一包含：

```json
{
  "type": "team.v2.snapshot",
  "teamId": "server-team-id",
  "revision": 3,
  "payload": {}
}
```

### 8.2 队伍指令

```text
team.v2.create
team.v2.invite
team.v2.invite.respond
team.v2.leave
team.v2.kick
team.v2.disband
team.v2.snapshot.request
```

服务端事件：

```text
team.v2.command.result
team.v2.invite.received
team.v2.snapshot
team.v2.disbanded
team.v2.presence
```

客户端不能在 payload 中指定自己的账号、队长账号或最终成员列表。

### 8.3 队伍切图协议

1. 队长先通过个人传送接口申请服务端票据。
2. 服务端消费队长票据并接受 canonical 地图变化。
3. `TeamTravelRuntime` 创建 `transferId`。
4. 服务端为每名仍在队伍内且在线的成员签发独立票据。
5. 成员收到 `team.v2.travel.offer` 后加载目标地图。
6. 成员使用个人票据提交目标状态。
7. 服务端确认 canonical 位置后发送 `team.v2.travel.member`。
8. 全部完成、跳过或失败后发送 `team.v2.travel.completed`。

客户端不共享队长票据，不上传可信目标坐标，也不依赖房间广播推测跨图授权。

### 8.4 战斗协议

建局使用认证 HTTP：

```text
POST /api/online-battle/v2/start
```

服务端事件：

```text
battle.v2.started
battle.v2.choice.accepted
battle.v2.round
battle.v2.ended
battle.v2.recovered
```

每次选择必须匹配：

- authenticated account
- battleId
- round
- 本账号拥有的 fighterId

每个回合结果包含单调递增 `resultSequence`。旧回合、重复结果和非参战账号消息均明确拒绝或幂等忽略。

## 9. 分阶段实施

### 阶段 0：恢复可控基线

1. 确认当前 `app.js`、`index.html` 登录媒体改动归属。
2. 跑通现有队伍、联网战斗、遭遇、安全和启动测试。
3. 用两个真实浏览器账号复现组队、切图和战斗失败。
4. 保存 WS/HTTP 消息序列为测试夹具。
5. 基线提交后从 `develop` 创建 `feature/team-v2`。

验收：工作区意图明确，旧问题存在稳定自动化复现。

### 阶段 1：消除入口双份队伍写入

1. 将 `server.js` 中旧队伍元数据处理迁入 `队伍/`。
2. 让 `队伍/server.js` 成为唯一 canonical roster 写入者。
3. `server.js` 只调用 `teamRuntime.handleMessage(...)`。
4. 先保持现有协议行为不变，单独提交纯重构。

验收：旧队伍测试全绿；入口不再直接修改 team meta。

### 阶段 2：V2 共享协议与状态机

1. 新增 `队伍/shared.js`，定义消息、快照、校验与 error code。
2. 实现 `teamId`、`revision` 和 `requestId` 幂等。
3. 实现创建、邀请、接受、拒绝、离队、踢人、解散和重连。
4. V2 先以 shadow 模式运行，对比 V1/V2 状态，不驱动客户端。

验收：1～4 人状态机、重复指令、乱序、跨 realm、冒充和重连测试通过。

### 阶段 3：客户端队伍控制器

1. 从 `app.js` 迁出邀请、加入、离队、解散和 snapshot 应用逻辑。
2. 客户端只保存最新 V2 snapshot 与 pending command。
3. UI 不再直接写 `state.team.members`。
4. 使用 `TEAM_V2_ENABLED` 功能开关灰度切换。

验收：入口只接线；双端创建、邀请、离队、踢人、解散和重连 E2E 通过。

### 阶段 4：服务端 canonical 位置与个人传送票据

1. 新增 `position-runtime.js`，按账号和 realm 保存在线 canonical 位置。
2. 新增一次性 `travel-ticket-runtime.js`。
3. 票据绑定账号、realm、起点、目标、有效期和使用次数。
4. 普通跨图先切换到服务端票据，验证地图清单白名单和路径。
5. 位置拒绝进入 `recordAnomaly`，不接受客户端自行跨图。

验收：伪造地图、坐标、账号、重复票据和过期票据全部失败；正常单人切图可用。

### 阶段 5：队伍切图协调器

1. 实现 TeamTransfer 与每成员独立票据。
2. 处理队长连续切图、成员加载慢、票据过期、离队、换线和断线。
3. 客户端展示“跟随中/已到达/失败”，不永久锁死移动。
4. 自动重签限制次数，超过后明确失败并允许手动重试。

验收：2～4 个浏览器上下文连续切图 20 次，无在线成员永久停留旧图。

### 阶段 6：拆分联网战斗服务端

1. 从 `联网战斗/runtime.js` 原样抽出 session store、participant builder、round runtime 和 lifecycle。
2. 纯重构单独提交，行为保持不变。
3. 引入 frozen roster、round、resultSequence 和账号 ownership。
4. PVE/PVP 共用生命周期，保留各自建局、目标和奖励校验。

验收：旧战斗测试全绿；新模块能独立测试建局、选择、回合、结束和清理。

### 阶段 7：V2 组队战斗

1. 建局时校验队长、队伍 revision、canonical 地图和成员状态。
2. 参战名单冻结，fighter ownership 绑定账号。
3. 超时玩家使用服务端自动操作，不重置整轮 deadline。
4. 队伍解散、成员逃跑、全员断线按明确规则结束。
5. 重连账号通过 `battle.v2.recovered` 恢复当前快照。
6. PVE 每个账号获得独立奖励票据，领取保持事务与幂等。

验收：2～4 人 PVE、队对队 PVP、断线恢复、逃跑、解散和奖励全部通过。

### 阶段 8：客户端在线战斗控制器

1. 从 `app.js` 迁出 online battle inbox 和 started/round/ended/recovered 处理。
2. 客户端只渲染服务端结果，不自行结束或重算在线战斗。
3. 缓存资源加载期间到达的回合、奖励和结束消息。
4. 上一场退场动画完成后再挂载下一场 battleId。

验收：不同网络延迟下所有成员进入、推进和退出同一场战斗。

### 阶段 9：切换并删除 V1

1. 开发环境默认启用 V2，保留 V1 一轮回归周期。
2. 对比 V1/V2 日志与行为。
3. 达到验收门槛后删除旧 team 消息、客户端 roster 写入和旧战斗分支。
4. 更新 API、README、安全和运维排障文档。

验收：全局搜索无 V1/V2 双份真理；入口只剩接线。

## 10. 测试计划

### 10.1 单元测试

- 邀请过期、重复接受、重复离队。
- 非队长踢人或解散。
- revision 单调递增，旧快照忽略。
- 同账号更换 `peerId`，其他账号复用旧 `peerId`。
- 传送票据绑定、过期、重复消费和目标篡改。
- fighter ownership、旧 round、重复 choice、超时选择。

### 10.2 集成测试

- 两人、三人、四人完整队伍生命周期。
- 队长与成员分别断线重连。
- 切图中离队、连续切图、换线路和加载失败。
- PVE、队对队 PVP、成员阵亡、逃跑和解散。
- 战斗胜利后每账号独立奖励，重复领取不双发。

### 10.3 Playwright 多客户端 E2E

使用 2～4 个独立 browser context：

1. 登录同一线路。
2. 创建并加入队伍。
3. 连续跨图并查询服务端 canonical 地图。
4. 触发组队 PVE，确认所有成员进入同一 battleId。
5. 每人提交选择，确认 round 和 resultSequence 一致。
6. 战斗结束后全部回图，奖励每人只发一次。
7. 在切图、建局和回合中分别断网并验证恢复。

### 10.4 安全与稳定性

- 伪造 account、leader、members、map、fighterId、round 和 reward。
- 消息重复、乱序、延迟和丢包注入。
- 100 个并发队伍执行邀请、切图和战斗建局。
- 检查断线宽限期、邀请、transfer 和 battle session 无泄漏。

```text

team_command_rejected
team_transfer_started
team_transfer_member_failed
battle_session_started
```

## 14. 最终验收门槛

- 2～4 人连续组队、离队、踢人、解散无幽灵成员。
- 队长或成员更换 `peerId` 后按账号恢复。
- 连续切图 20 次，在线跟随成员最终收敛到正确地图。
- PVE/PVP 所有参战者收到相同 battleId、round 和 resultSequence。
- 未参战账号不能提交选择、结束战斗或领取奖励。
- 重复选择、重复结束、重复切图和重复领奖均幂等。
- 断线重连能恢复队伍和战斗，超出宽限期能明确清理。
- 单元、集成、E2E、安全、压力和启动测试全部通过。
- `app.js`、`server.js` 不保留 V1/V2 双份业务实现。

## 15. 开工前置条件

当前工作区只有 `app.js`、`index.html` 和登录媒体模块相关未提交改动。正式开始 V2 前，应先确认并提交或隔离这些改动，然后执行阶段 0，建立干净、可测试、可回滚的组队重做基线。
