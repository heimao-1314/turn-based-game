# 全服竞技场系统说明与迁移指南

> 用途：可单独复制到其他项目，作为策划说明、技术设计和开发验收依据。
> 核对日期：2026-09-13；代码基线：`6f293db`。
> 第 1～8 节描述现有实现；第 9～11 节给出迁移要求与验收标准。标注为“建议”的内容不代表原项目已经实现。

## 1. 系统定位

这是一个异步镜像 PvP 排名系统。玩家上传一套防守阵容，其他玩家随时挑战该阵容，不需要防守者在线。挑战者可逐回合操作，防守方由服务器自动操作；服务器决定战斗结果，胜利后改变排名。每天中午以后，上榜玩家可按规则领取排名奖励。

“全服”在本项目指同一区服内所有频道共享榜单：不同 `server_id` 的榜单独立，并非所有区服混在一个跨服榜。一个登录账号可有不同区服角色，竞技场身份使用角色账号 `characterAccount`，不能直接把登录账号当参赛角色。

| 项目 | 当前规则 |
|---|---|
| 榜单容量 | 每区服 100 个名次，数字越小越好 |
| 空位展示 | 自动展示 NPC“阿木木”，无需真实数据库记录 |
| 每方阵容 | 角色 1 名、宠物最多 1 只、佣兵最多 1 名 |
| 排名机制 | 挑战胜利占位或换位，无积分、Elo、段位计算 |
| 挑战范围 | 未上榜可打 91～100；已上榜可打自己前面最近 10 名 |
| 防守数据 | 上传时保存的服务器权威快照 |
| 主要战斗方式 | HTTP 创建战斗、逐回合提交指令、服务器返回战报 |
| 奖励 | 每日 12:00 后手动领取；按领取时排名 |
| 未实现的玩法限制 | 竞技场模块没有每日挑战次数、挑战消耗、冷却、赛季或离线防守战报系统 |

## 2. 玩家操作与完整流程

### 2.1 菜单

进入“全服竞技场”后显示当前排名或“未上榜”，提供四个入口：

1. **上传数据**：保存当前防守阵容；未上榜时尝试获得空位。
2. **查看名次**：查看全部 100 个名次、名称及 NPC 占位标识。
3. **领取奖励**：服务器检查时间、名次和当日领取记录后发放。
4. **发起挑战**：只展示当前允许挑战的目标；选择后进入战斗。

排行榜读取失败显示失败条目；无目标时显示“当前没有可挑战名次”。第 1 名没有可向上挑战的目标。

### 2.2 首次上传与更新

- 已上榜：保持名次，覆盖该名次的防守快照和更新时间。
- 未上榜：从第 100 名向第 1 名扫描，找到第一个没有真人记录的位置，直接占据该位置。
- 所有位置都有真人：返回 `arena_full`，但未上榜玩家仍可通过挑战第 91～100 名进入榜单。
- 上传本身不要求战斗胜利。上传查找空位没有“仅后十名”的限制，因此榜单存在靠前空洞时，也可能直接进入靠前名次。

客户端上传前会先保存玩家状态，再发送镜像提示。最终战斗属性由服务器从玩家记录计算。

### 2.3 挑战资格

设当前名次为 `r`，目标名次为 `t`；未上榜记为 `r = 0`：

```text
r = 0：91 ≤ t ≤ 100
r > 0：max(1, r - 10) ≤ t < r
```

例如第 50 名可挑战第 40～49 名，第 7 名可挑战第 1～6 名。不能挑战自己或更低名次。

### 2.4 胜败与名次变化

| 挑战者原状态 | 目标状态 | 挑战成功后的变化 |
|---|---|---|
| 未上榜 | 真人 | 挑战者进入目标名次，原防守者掉出榜单 |
| 未上榜 | NPC 空位 | 挑战者进入目标名次 |
| 已上榜 | 真人 | 挑战者与目标位置上的真人交换名次 |
| 已上榜 | NPC 空位 | 挑战者进入目标名次，自己的原位置清空并显示 NPC |

失败、平局或主动取消不改变名次。战斗胜利本身不发放日排名奖励，玩家必须单独点击领取。

**现实现细节**：胜利落库时重新读取双方位置，没有检查目标位置是否还是开战时的防守者。因此长战斗期间被其他人抢位，会出现“打的是旧镜像，换位的是结算时占位者”。迁移时应按第 9 节处理。

## 3. 防守镜像与阵容

### 3.1 进攻与防守的区别

- 进攻阵容：开战时从服务器当前角色数据计算。
- 防守阵容：读取目标排名记录的 `mirror_json`，不按防守者当前实时装备重算。
- 装备、宠物、佣兵或自动策略发生变化后，需要再次上传才能更新已有防守镜像。
- 胜利后保存到新名次的防守镜像优先沿用自己之前上传的有效快照；不存在有效快照才从当前数据生成。因此“进攻使用新装备获胜”不等于“防守装备自动刷新”。

### 3.2 数据结构

下面是结构示意，属性数值不是配置默认值：

```json
{
  "actor": {
    "name": "角色名称",
    "spriteId": 895,
    "stats": { "hp": 10000, "attack": 1000, "defense": 500, "speed": 100, "skillId": "shining_strike" }
  },
  "pet": null,
  "mercenary": null,
  "selection": {},
  "_server": {
    "row": {
      "account": "角色标识",
      "selection_json": "{}",
      "equipment_json": "[]",
      "equipped_json": "{}",
      "auto_strategy_json": "{}",
      "active_mercenary_id": "",
      "mercenaries_json": "[]",
      "mercenary_necklaces_json": "[]",
      "mercenary_orbs_json": "[]"
    },
    "activeMercenary": null
  }
}
```

`pet` 存在时含名称、精灵 ID 和属性；`mercenary` 还包含 `id`、`type`、`passiveSkills`、`extraSkills`。属性可包含 `mana`、`crit`、`critDamage`、`skillIds` 等，含义由战斗系统定义。

`_server` 用于服务器重建职业技能条件、装备条件、自动策略及佣兵效果，不能发送给浏览器。当前模块通过 `publicMirror()` 移除此字段后返回公开镜像。

客户端提交的攻击、防御等属性不作为真值；服务器使用 `statsForPlayerRow`、`statsForPetRow`、`statsForMercenaryRow` 计算。客户端可提示宠物 ID，但必须属于服务器确认的已拥有宠物集合。角色外观 ID、宠物名称等展示信息仍可能来自客户端，迁移时应做范围校验和安全渲染。

### 3.3 NPC 默认配置

所有空位 NPC 使用相同属性，只有名字和虚拟账号带名次编号：

| 字段 | 值 |
|---|---|
| 名称 / 虚拟账号 | `阿木木{rank}` / `arena_amumu_{rank}` |
| 精灵 ID | 895 |
| 生命 / 防御 / 速度 | 118000 / 14500 / 1350 |
| 攻击 / mana | 18500 / 2600 |
| 暴击 / 暴击伤害 | 6 / 240 |
| 技能 | `wild_amumu` |
| 宠物 / 佣兵 | 无 |

这些值是原游戏数值，复用玩法时应按目标项目的成长曲线重新配置。

## 4. 战斗与回合协议

### 4.1 主流程

```text
查看目标 → start 校验资格并创建服务器会话
         → 返回双方公开镜像及 battleId
         → 客户端选指令并提交 turn
         → 服务器清洗进攻指令、生成防守指令、运算一个回合
         → 返回事件序列和双方最终状态
         → 客户端播放动画并同步状态
         → 未结束则继续 turn；结束则服务器结算名次并删除会话
```

该流程使用 HTTP，不要求为竞技场建立专属 WebSocket 房间，也不等待防守者确认。

### 4.2 指令

推荐按单位 `battleId` 组织指令，避免同名角色混淆：

```json
{
  "battleId": "start返回的战斗ID",
  "choice": {
    "actions": {
      "单位battleId": { "type": "skill", "skillId": "shining_strike", "target": "目标单位battleId" }
    }
  }
}
```

也兼容 `choice.actor`、`choice.pet`、`choice.mercenary`。普通攻击用 `type: "attack"`。服务器只接受属于己方的单位引用；非法或不可用技能回退到可用默认技能，目标无效时由服务器选择存活目标。

技能可用性包含技能目录、角色职业、武器和魔兵类型，以及献祭技能所需队友是否存在。具体伤害公式、状态效果和被动属于共享战斗引擎，不是竞技场独有公式。

### 4.3 防守自动策略

镜像中保存的 `auto_strategy_json` 按以下键读取：

- `actor`：主角策略。
- `petById[宠物精灵ID]`：宠物策略。
- `mercenaryById[佣兵ID]`：佣兵策略。

每项含 `mode`（`attack` 或 `skill`）和可选 `skillId`。无效技能回退；强制普攻单位只普攻。默认目标是对方第一个存活单位。佣兵默认技能选择对 `holy_elf_spring` 有优先处理。

### 4.4 回合结果

核心 `result` 包含：

| 字段 | 含义 |
|---|---|
| `events` | 按播放顺序排列的攻击、技能、状态等事件 |
| `hp.ally` / `hp.enemy` | 双方单位状态数组 |
| `done` | 是否结束 |
| `winner` | `ally` 进攻获胜、`enemy` 防守获胜、空字符串无胜方 |

单位状态除了 `hp` 和 `defeated`，还包括 `battleId`、`maxHp`、`statuses`、`buffs`、复活使用标记、减伤变化和属性倍率等。不能只同步血量而丢弃这些持续状态。

引擎按有效速度降序行动，同速随机排序；处理控制、被动、行动和回合末持续伤害。一方全灭即结束；双方都无存活单位时胜方为空，不换位。引擎返回结果后会恢复计算前状态，竞技场适配层必须应用返回的状态快照，才能正确继续下一回合。

### 4.5 一次性自动挑战

另有 `/api/arena/challenge`，服务器一次性自动模拟双方，最多 60 回合。若仍未分胜负，比较双方存活单位剩余生命总和，相等时进攻方胜。接口只返回摘要和回合数量，不返回完整回放。

**60 回合上限仅作用于此一次性接口。当前逐回合 `start/turn` 流程没有执行同样的上限。** 两种模式应在迁移时统一规则。

## 5. 每日排名奖励

### 5.1 当前奖励表

| 领取时名次 | 灵魂粉末 `soulPowder` | 仙丹 `immortalPill` |
|---|---:|---:|
| 1 | 5000 | 20 |
| 2 | 3000 | 15 |
| 3 | 2000 | 10 |
| 4 | 0 | 0 |
| 5～10 | 1000 | 5 |
| 11～100 | 500 | 2 |
| 未上榜 | 0 | 0 |

第 4 名没有匹配奖励区间，会返回 `not_qualified`。这是当前代码事实，不能擅自解释成已经实现“4～10 名同奖”；其他项目应显式决定并修正区间。

### 5.2 时间与领取语义

- 使用服务器进程本地时区，日期键格式为 `YYYY-MM-DD`。
- 当日 12:00 前拒绝领取；12:00 后至当天结束可手动领取一次。
- 没有 12:00 排名快照，也没有定时批量发奖任务；按点击领取时的实时名次计算。
- 玩家字段 `arena_reward_claimed_key` 等于今天时拒绝再次领取。
- 今天领取后再提高排名，不能补领差额；今天漏领也没有补发逻辑。
- 一条玩家 `UPDATE` 同时增加两种资源并写入日期键；接口另外返回更新后的 `player`，客户端据此刷新余额。

举例：12:00 是第 20 名，13:00 升到第 3 名，13:05 首次领取可得第 3 名奖励；若 12:05 已领取第 20 名奖励，则当天不能再领。

## 6. HTTP 接口清单

成功通常返回 `{ "ok": true, ... }`；失败返回 `{ "ok": false, "error": "错误码", ... }` 并设置对应 HTTP 状态。客户端使用项目会话凭据；写接口身份由会话解析，不能用 body 中的 `account` 冒充。

| 方法与路径 | 输入 | 成功结果要点 |
|---|---|---|
| `GET /api/arena/rankings` | 可选 `serverId`；已登录以会话区服为准 | `rankings[100]`、`myRank`、`challengeRankings` |
| `POST /api/arena/upload` | 可选 `mirror` 提示 | `rank`、`name`、公开 `mirror` |
| `POST /api/arena/start` | `rank`、可选 `mirror` | `battleId`、`rank`、`currentRank`、`attacker`、`defender` |
| `POST /api/arena/turn` | `battleId`、`choice` | `result`、`rank`、`oldRank`、`swapped`、`won` |
| `POST /api/arena/cancel` | `battleId` | `{ok:true}`，只删除属于自己的会话 |
| `POST /api/arena/claim-reward` | 无业务必填参数 | `key`、`rank`、两种奖励数量、`player` |
| `POST /api/arena/challenge` | `rank`、可选 `mirror` | 自动挑战摘要：`won`、`winner`、`rounds`、排名变更、对手摘要、进攻镜像 |
| `POST /api/arena/occupy` | `rank`、可选 `mirror` | 旧直接占位接口；迁移时禁止作为客户端公开能力 |
| `POST /api/admin/reset-arena` | 管理凭据 | 清空所有区服排名记录，返回 `{ok:true}` |

`rankings` 允许匿名读取，此时 `myRank=0`；查询参数 `account` 不用于认定当前角色。单个排名条目含 `rank`、`account`、`name`、`mirror`、`isNpc`、`updatedAt`。NPC 的更新时间为空。

主要错误：

| HTTP | 错误码 | 含义 |
|---|---|---|
| 401 | `auth_required` | 缺少有效登录会话 |
| 409 | `character_required` / `server_session_invalid` / `character_session_invalid` | 角色或区服会话无效 |
| 404 | `player_not_found` | 角色不存在 |
| 409 | `arena_full` | 上传时没有空位 |
| 409 | `rank_not_allowed` | 不在可挑战范围 |
| 409 | `self_rank` | 自己的名次，存在防御性校验 |
| 404 | `battle_not_found` | 会话不存在、已结束、重启丢失或不属于调用者 |
| 409 | `before_settlement` | 尚未到每日 12:00 |
| 409 | `already_claimed` | 当天已领取 |
| 409 | `not_qualified` | 当前名次无奖励 |

模块虽有 `invalid_rank` 分支，但当前先把输入夹到 1～100，不能据此认为已严格校验整数。新项目应拒绝缺失、非整数、非有限数和越界值。

## 7. 持久化与运行时状态

### 7.1 排名表

当前迁移后的核心结构如下，默认区服值应由目标项目配置：

```sql
CREATE TABLE arena_rankings (
  server_id TEXT NOT NULL,
  rank INTEGER NOT NULL,
  account TEXT NOT NULL,
  name TEXT NOT NULL,
  mirror_json TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  PRIMARY KEY (server_id, rank),
  UNIQUE (server_id, account)
);
```

同区服一个位置只能有一个真人，一个角色只能占一个位置。NPC 不入表。玩家表另需 `arena_reward_claimed_key`（默认空字符串）、`soul_powder` 和 `immortal_pill`，或目标项目对应的资产记录。

### 7.2 战斗会话

`activeSessions` 是单进程内存 Map，按 `battleId` 保存账号、目标名次、开战时名次、防守者、用于占位的防守快照、创建时间、回合数、战斗引擎及双方状态。

当前会话 ID 使用时间戳和 `Math.random()`；创建时间没有用于过期清理，也没有每角色单场限制。进程重启后会话丢失。结束或主动取消会删除会话；客户端异常离开不保证主动取消成功。

### 7.3 管理重置

当前重置接口删除整张排名表的数据，所有区服重新显示 NPC。它不清除玩家当日领奖标记，也不清除正在进行的内存战斗；旧战斗之后仍可能写回名次。迁移时应增加区服范围、榜单版本和会话失效策略。

## 9. 迁移时必须处理的实现缺口

以下是基于源码的迁移注意项，本次仅形成文档，没有修改现有业务。

1. **关闭直接占位入口。** 现有 `/api/arena/occupy` 虽经过角色鉴权和挑战范围检查，却不要求服务器胜利凭证。新项目应删除该客户端接口，占位只能由服务器已完成战斗触发。
2. **排名交换必须原子化。** 当前换位是多条独立 SQL，且使用 `INSERT OR REPLACE`。唯一约束冲突会隐式替换记录，中途失败可能破坏排名。新项目应在同一事务中检查、移除双方旧位置并写入新位置，失败整体回滚。
3. **明确开战后目标变化规则。** 推荐保存榜单/位置版本及防守角色 ID；结算事务中发现目标版本变化时，返回明确失效结果，不覆盖另一个未经挑战的玩家。也可设计锁位，但需超时释放。
4. **回合与最终结算幂等。** 当前没有回合序号校验，相同 `turn` 请求重放会推进下一回合。建议加入 `expectedTurn` 和 `requestId`，重复请求返回已保存结果；同一战斗只能占位一次。
5. **支持会话清理与部署拓扑。** 增加 TTL、每角色活动场数限制和速率限制。多实例部署需共享会话或明确会话归属；持久化战斗或定义重启失效策略。战斗 ID 使用可靠随机 ID。
6. **领奖并发保护。** 当前先读日期键再执行无条件资产更新，单进程同步调用能避免该段异步交错，但不提供多进程并发保障。建议使用事务及 `(区服,角色,奖励日期)` 唯一领奖记录，资产发放与记账一起提交。
7. **明确奖励产品规则。** 修正或确认第 4 名奖励；配置明确时区；在“领取时实时排名”和“12:00 固定快照”中明确选择。若选固定快照，需要新增持久化快照及补偿机制。
8. **统一两种战斗模式。** 逐回合模式增加回合上限与超时裁决；公平性敏感项目可只暴露一种挑战模式。取消、平局和超时是否计次也应配置。
9. **重置隔离旧战斗。** 管理重置必须按明确区服执行，并使旧版本战斗无法重新写榜；是否重置领奖资格需要独立规则。
10. **保持公开数据最小化。** 使用公开角色 ID，避免公开登录凭据标识；禁止返回 `_server`、装备原始背包或完整玩家行；所有动态名称安全渲染。排名和资产关键变更需可审计。

## 10. 给其他项目的推荐实现结构

这是目标设计建议，可更换语言、框架和数据库，但保持以下职责边界：

```text
arena/
  rules              排名范围、NPC、奖励、时间规则
  service            上传、挑战、结算、领取的用例编排
  repository         排名、会话、领奖记录与事务
  battle-adapter     目标战斗引擎适配与公开状态转换
  player-adapter     身份、服务器属性、阵容、资产接口
  routes             HTTP 鉴权、输入校验、错误映射
  client             菜单、挑战交互、战报播放
```

建议配置化：榜单容量（100）、可挑战跨度（10）、首次挑战范围（末 10 名）、NPC 模板、奖励区间、业务时区、领取开始时间（12:00）、回合上限（60）、战斗 TTL、每日次数及消耗（原版无）。

建议实施顺序：

1. 确认玩法配置及第 9 节产品决策，建立角色、区服和数据库约束。
2. 实现只读榜单和服务器阵容快照，再实现上传与首次占位。
3. 接入战斗引擎，实现创建、回合幂等、取消和过期。
4. 实现含版本校验的事务换位，禁止客户端直接提交胜利。
5. 实现事务领奖、唯一领奖记录和资产同步。
6. 接入菜单、战报动画、断线恢复提示、管理重置和审计。

可直接交给其他项目开发者或 AI 的需求摘要：

> 实现一个按区服隔离的 100 名异步镜像竞技场。每方角色、宠物、佣兵各最多一个，属性由服务器计算。玩家上传防守快照，未上榜上传可占最低空位；榜满后通过挑战进入。未上榜仅挑战末 10 名，已上榜仅挑战前方最近 10 名。服务器逐回合裁决，胜利按占位/换位规则更新排名，失败不动排名。每日指定时区 12:00 后按明确的排名取值规则领取一次奖励。使用本文描述的数据、接口和交互，实施第 9 节的原子性、版本控制、幂等、会话过期及接口收口要求；第 4 名奖励必须明确配置。不要依赖客户端计算属性、胜负或资源增量。

## 11. 目标项目验收清单

以下是迁移完成后应执行的验收，不代表本次已经运行通过：

| 场景 | 预期 |
|---|---|
| 空榜查询 | 返回 100 个 NPC；不同区服互不干扰 |
| 首次上传 / 重复上传 | 依次占最低空位；重复上传只更新自己的快照 |
| 榜满上传 | `arena_full`，不覆盖真人 |
| 挑战边界 | 未上榜只允许末十名；第 50 名只允许 40～49；第 1 名无目标 |
| 四类成功占位 | 与第 2.4 节表格一致，角色不重复占位 |
| 失败 / 平局 / 取消 | 排名不变，活动会话正确终止 |
| 伪造属性或胜利 | 不改变权威数值，不能直接占位 |
| 越权回合 | 无法操作其他角色会话 |
| 防守快照 | 未再次上传时保持旧阵容和自动策略 |
| 重放 turn / 重试结算 | 同一回合不重复推进，同一胜利不重复换位 |
| 同时抢同一名次 | 按版本/锁位规则确定结果，无错换、丢人或双占 |
| 中途数据库失败 | 排名交换、领奖资产全部回滚 |
| 11:59 / 12:00 / 跨日 | 按配置时区准确限制；一天只能成功领取一次 |
| 奖励区间边界 | 覆盖 1、2、3、4、5、10、11、100 及未上榜 |
| 并发领奖 | 只发一次，成功后余额和领奖记录一致 |
| 战斗超时 / 进程重启 | 结果符合恢复或失效约定，无永久泄漏会话 |
| 重置期间有旧战斗 | 旧战斗不能恢复旧榜，其他区服不误清 |
| 公开响应 | 不包含服务器私有镜像字段、凭据或完整玩家记录 |

仅有排行榜展示和正常挑战成功不足以验收；排名交换、领奖和会话在并发、重试、重启时的行为同样属于系统定义。
